# FMT-Model-2025b 设计项关系图

最后更新:2026-05-05
配套文件:[00-design-plan.md](00-design-plan.md)、[INDEX.md](INDEX.md)

## 1. 目的

显式记录设计工作项之间的**依赖关系**与**信息流**,以便:

- 决定工作项的执行顺序
- 在某一项设计变更时,快速识别需要回溯审阅的下游项
- 防止设计文档之间互相引用却没有明确指向

## 2. 关系类型

本图中的边定义如下:

| 关系符号 | 含义 |
|---|---|
| `A → B` | A 是 B 的**强前置**(B 启动前 A 必须完成) |
| `A ⇢ B` | A 为 B 提供**信息输入**(B 启动时 A 应稳定,但允许并行修订) |
| `A ↔ B` | A 与 B **协同设计**(必须一起评审、一起定稿) |

## 4. 工作项级详细依赖

### 4.1 A 区(架构细化)

```text
架构 v1 → A1
A1 → A2
A1 → A4
A1 → A5
A2, A4, A5 → A3
```

变更影响:
- **A2 命名变更** → 几乎全仓库下游需回溯重命名(高代价,尽早冻结)
- **A4 跨速率变更** → G2 调度、E5 性能预算、C4 数值
- **A5 变体策略变更** → C2/D2/E2 结构设计、G1 顶层

### 4.2 B 区(契约)

```text
A3 → B1
A3 → B2
A3 → B3
B1 ↔ B2 ↔ B3            (字段类型 / 枚举 / 参数三者交叉引用,需协同定稿)
B1, B2, B3 → B4
B1 → B5                   (INS_Out_Bus 是 B1 的子集,但单列以强调跨仓库镜像流程)
```

变更影响:
- 任一 B 项变更都会沿 ⇢ 流向所有 C/D/E/F,并触发 B4/B5 的策略复审。

### 4.3 C 区(Plant)

```text
A3, B1 ⇢ C1
C1 → C2
C2 → C3
C1 → C4                   (积分与数值约束受功能保真度等级影响)
C2, C4 ⇢ G1               (Plant 顶层接入 Harness)
```

### 4.4 D 区(FMS)

```text
A3, B1, B2 ⇢ D1
D1 → D2
D2 → D3                   (Mode Manager 在结构边界确定后再做 Stateflow 详细)
D2 → D4                   (Command Shaper 同上)
D3, D4 → D5
D3, D4 ↔ D6               (Mode + Shaper 与 cmd_mask 语义协同定稿)
```

### 4.5 E 区(Controller)

```text
A3, B1, B2 ⇢ E1
D6 → E1                   (cmd_mask 语义决定 E1 的环路裁剪规则)
                          注:E1 整体推迟到 Wave 8 与 D6 同 batch,见 §6
E1 → E2
E2 → E3
E3 → E4
E3 → E5                   (性能预算严格依赖算法粒度,改为强前置)
E1 ⇢ E5                   (E5 也用 E1 的环路清单,但弱依赖)
```

### 4.6 F 区(INS 契约消费)

```text
B5 → F1
C1 ⇢ F1                   (ins_stub 输入是 Plant_States_Bus,需了解 Plant 输出能力)
F1 → F2
B5, D1, E1 ⇢ F3           (消费规则需了解 FMS/Controller 对哪些字段有依赖)
```

### 4.7 G 区(Harness)

```text
A4 → G2
C2, D2, E2, F2 ⇢ G1
G1, G2 → G3
G1 → G4
```

### 4.8 H 区(验证)

```text
D1, E1 ⇢ H1               (功能设计决定 golden path 与边界场景)
D6, B1 ⇢ H2               (指标定义在哪些字段上量化)
H1, H2 → H3
G3 ⇢ H3                   (回归基线复用 G3 的 logsout 配置)
```

### 4.9 I 区(工具)

I 区设计与主干并行,但有以下信息流:

```text
B1, B2, B3 ⇢ I2           (镜像脚本需消费 B 区清单)
B4 ↔ I3                   (策略与脚本是同一件事的两面:策略定义 What,脚本设计定义 How)
A2 ⇢ I1                   (init 脚本遵守命名规则)
A3, B1 ⇢ I4               (codegen 配置需了解模块边界与 bus)
G1, H1, H3 ⇢ I5           (sim runner 服务于 Harness 与验证)
```

### 4.10 新增项(2026-05-05 审计闭合)

```text
A1 → A6                   (init/reset 状态契约)
A1 → A7                   (时间/时间戳约定)
A1 → A8                   (共享库块清单)
A6 ⇢ B3, C1, C4, D1, E1   (init/reset 影响参数初值与各模块复位行为)
A7 ⇢ A4, G2, C4, E5       (时间约定影响速率边界、调度、积分、性能预算)
A8 ⇢ C2, D2, E2           (库块归属与结构设计协同)

H4 ⇢ F1                   (故障注入与 ins_stub 噪声/偏差/延迟知识共享)
H4 ↔ H1                   (故障场景与场景目录协同)
```

## 5. 设计协同对(必须同时评审定稿)

以下成对/成组工作项的产出必须在同一次评审会上一起冻结,否则会出现接口不一致:

1. **(B1, B2, B3)** — bus / enum / parameter 三件套
2. **(D3, D4, D6, E1)** — Mode Manager / Command Shaper / cmd_mask 语义 / Controller 功能(含环路裁剪规则)。E1 与 D6 由强前置升级为同 batch
3. **(B4, I3)** — 契约 diff 策略与脚本设计
4. **(H1, H4)** — 验证场景目录与故障注入目录

## 6. 推荐执行顺序(基于关系图的拓扑)

下面顺序仅满足依赖约束;具体启动时机由用户决定。**注:以下是设计文档撰写顺序,不是实现顺序。**

```text
Wave 1:  A1
Wave 2:  A2, A4, A5, A6, A7, A8 (并行;A6/A7/A8 为 2026-05-05 审计新增)
Wave 3:  A3
Wave 4:  B1 + B2 + B3          (协同定稿,作为一个 batch)
Wave 5:  B4 + B5 + (I2, I3 起草)(并行;B4 与 I3 协同)
Wave 6:  C1, D1, F1            (并行;E1 已撤出本 Wave,推迟到 Wave 8)
Wave 7:  C2, D2, E2, F2        (并行)
Wave 8:  D3 + D4 + D6 + E1     (协同定稿 batch;E1 与 D6 同 batch)
Wave 9:  C3, C4, D5, E3, E4, F3  (E5 撤出,移至 Wave 10)
Wave 10: G1, G2, G3, G4, E5    (E5 改入 Wave 10 以满足 E3 → E5 强前置)
Wave 11: H1, H2, H3, H4        (H4 与 H1 同 batch)
Wave 12: I1, I4, I5            (收尾;前置已完成)
```

## 7. 变更回溯规则

当任意已完成设计文档发生修订时:

1. 在 `INDEX.md` 决策日志追加一条记录,注明变更原因。
2. 沿本图所有出边(`→`、`⇢`、`↔`)向下游列出**受影响的工作项**。
3. 若有受影响下游已完成,在其文档顶部添加 `Affected by upstream change: <ID, date>` 标记,并安排复审。
4. 若变更触及 firmware 契约,额外在架构文档的 §17 风险或 §5 契约约束中登记。

## 8. 关系图维护

本文件随设计推进更新:

- **新增工作项**时:在 §4 对应区块添加依赖,并更新 §3 顶层图。
- **拆分工作项**时:保留原 ID 为父节点,子节点用 `<原 ID>.x` 命名。
- **删除工作项**时:在本文件保留一条划线条目(如 `~~D7~~ 已合并至 D4`),以维持决策追溯。
